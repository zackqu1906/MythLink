# 2026-09-28 语音／手势卡住的根因与修复

## 现场证据

来源：`logs/diagnostic.log`，运行 `351b232d`，Ringo8F56，ADPCM 音频、固件手势、纯手势启停。

- 17:46:58.027：输入法返回与当前请求一致的 BEGIN 确认，`phase=listening`、`ready=true`。
- 17:46:58.028：同一句被主程序报为“已切换应用，本句已取消”，随后几毫秒内重复报错。
- 后续 11 次准备状态探测仍看到刚才那句的旧编号；它与新请求编号不同，应用不能放行新一句。
- 17:47:20.379：固件下滑事件已经到达，动作层记录 `blocked / speech_busy`。
- 同期 97 个固件手势均已分发，队列深度和丢弃数均为 0；连续录音文件仍增长，检查的音频片段也不是全零。

这组现象定位到输入法启动状态被错误取消，而非固件事件队列堵塞。

## 根因

`mac_workspace.refresh_workspace()` 原来每次查询前台应用都会执行约 5 ms 的 `NSRunLoop.runUntilDate_()`。
这最初用于没有事件循环的原生访问工作进程，使 NSWorkspace 的前台应用缓存保持更新。
但同一函数也被 Qt 界面线程用于输入法的启动检查。

在界面线程内，这个调用会嵌套处理 Qt／AppKit 消息。因此不是简单等待 5 ms：
它可以在 `_foreground_identity()` 尚未返回时，先处理输入法的 BEGIN 成功确认。
成功确认会清空 `_begin_origin`，终止准备阶段。
外层调用回来后，仍继续执行原来的比较：

```python
self._foreground_identity() == self._begin_origin
```

此时左侧还是刚读取的目标应用，右侧已经变为 `None`，于是误走“切换应用”的取消分支。
定时器、原生状态回调、输入法选择回调三条路径都有同样的重入问题。

误取消发生在 BEGIN 已成功之后，准备标记已经清除，主程序与原生输入法可能留下不一致的会话编号。
新一句因此一直等不到正确确认；应用中菜单／输入框选择等动作又依赖语音忙碌状态，造成“语音和手势一起卡住”的表象。

## 修复

1. 在 Qt 事件线程查询前台应用时不再主动嵌套运行 NSRunLoop，由已有事件循环处理通知。
   没有 Qt 事件循环的工作进程及后台线程仍保留刷新机制，防止引入旧的前台应用缓存问题。
2. 启动检查保存并核对连接、输入框、会话编号、目标应用、选择器及准备阶段。
   如果读取期间已成功、取消、重试或断连，旧调用立即退出，不再修改当前会话。
3. 真实前台应用变化仍会阻止启动，并记录预期／实际应用与 PID，便于区分真实切换与状态变化。

ADPCM、固件手势协议和动作绑定保持本次 SDK 更新后的设置。本次没有改动原生输入法程序。

## 验证

- 修复前，独立离线复现的 3 条路径全部错误地从 `listening` 变为 `error`。
- 修复后，同样的 3 条路径通过，并验证只确认一次、能够正常开始下一句。
- 新增取消、重试、断连发生在读取期间的覆盖，确认旧回调不能污染新状态。
- 验证 Qt 查询不运行嵌套事件循环，后台线程仍能刷新前台应用。
- 输入法生命周期、固件手势路由、语音模式及前台应用读取相关回归共 191 项通过。
- 行内输入 QML 测试 50 项通过，包含“确认消息在读取期间到达”的完整语音启动用例。
- 2026-09-29 重新构建 `dist/Proximic Voice.app` 和 `dist/ProximicVoice-0.6.0-macos-arm64.dmg`；签名、包兼容性、启动自检与 DMG 完整性校验通过。
- 冻结程序归档确认包含 `_on_qt_event_thread`／`_startup_context` 修复、public 协议与固件手势模块，且没有旧电脑端手势模型模块。构建日志：`.build/startup-race-20260929/build-macos.log`。

重新退出并启动主项目后生效；正常退出会让原生输入法清理旧连接的会话。真实切换应用与连续听写的硬件验收需在新进程中进行。
