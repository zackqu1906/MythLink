# 左点输入问题与候选层优化（2026-10-13）

后续已实现逐笔左点兼容及构件生成，使用方法与验证结果见 [左点兼容输入](LEFT_DOT_INPUT.md)。下文保留实施前的分析和标注初稿统计。

建议保留标准五类码表，增加按字、按笔顺变体记录的左点位置标注，在这些位置兼容点／撇，结合本次日志再兼容竖。轨迹输出继续保留实际识别类别；候选解释使用字形先验，不要求模型从形状相同的短撇中判断书写意图。

本轮完成离线数据核对、日志分析和标注初稿，未修改运行时输入法。清单是待复核数据，不是已经确认的全部左点。

## 现有补救为什么不够

`stroke_fuzzy.py` 已允许竖、撇、点之间的补救，但最佳类别距离必须不超过0.08，替代距离差必须不超过0.08；超过近邻范围的补救一个候选最多使用一次。稳定写成撇／竖的左点不一定接近现有右点模板，可能完全没有点类解释。若一个字有多个此类位置，也可能超过补救次数。

因此不能仅把轨迹阈值调宽。全局把撇、竖、点合并，会让正常笔画产生大量候选竞争。五类码 `n` 还包含捺；直接互换所有 `p/n` 会同时扩大捺的歧义。

## cnchar 与字形数据的核对

[cnchar 的 orderToWord 文档](https://github.com/theajack/cnchar#54-笔画序列推出原汉字-ordertoword)列出了独立的“点2”编码 `d`，普通点为 `k`，撇为 `s`，捺为 `l`。这里的字母是 cnchar 内部编码，与本项目 `hspnz` 不同。`orderToWord` 的模糊参数是包含／顺序／前缀查询，并不是按左点位置进行类别替代。

实际读取公开 npm 包 `cnchar-order@3.2.6` 内嵌数据，得到：

| 核对项 | 结果 |
| --- | ---: |
| 本项目3500常用字在 cnchar 中的覆盖 | 3500/3500 |
| 含“点2”的常用字 | 484字 |
| “点2”总位置数 | 509处 |
| 归并后的完整五类笔序已在本项目字典中 | 483/484字 |
| 对应字形笔画数量相同 | 484/484字 |
| “点2”示例轨迹首尾朝左下 | 463处 |
| “点2”示例轨迹为其他方向 | 46处 |

例子：宝／宇／实／穿／窗的第二笔、控的第五笔、快／情／心的第一笔、学的第四笔均标为“点2”。因此这份数据值得使用，而且可以直接生成逐笔初稿，不需要替换现有整套字库或在运行时引入 JavaScript。

但“点2”不能无条件等同于向左下的点。46处方向不一致主要涉及火部，例如火、灭、灰、炎、淡；左侧位置上的点在不同字形中可能向右下。cnchar 对“点2”的名称和形状说明本身也不足以给出完整语义定义，应结合具体字形复核。

“膝”的 cnchar 五类序列为 `pzhhhspnpnsnhnn`，本项目已有序列与其不同，不能按相同索引直接套标注。另外，普通点 `k` 中还找到“滚”第七笔、“翰”第十二笔的字形首尾向左下，列为补充待核查项，未直接认定为左点。

字形核验来自 [Make Me a Hanzi](https://github.com/skishore/makemeahanzi)：`graphics.txt` 提供按笔顺排列的 `medians`；`dictionary.txt` 提供构件分解与逐笔 `matches`，可以用于确认宀、忄、心、冖等构件。方向检查使用其原始坐标，向下的 y 值减少。笔数相同只支持初步对齐，不能证明每一笔顺序完全一致。[Hanzi Writer Data](https://github.com/chanind/hanzi-writer-data)也能提供这些字形，但其来源相同，不算另一份独立验证数据。

本轮字形方向筛查是离线标注辅助，不是让实时识别器根据用户轨迹区分左点／撇。自动得到初稿后，优先复核构件一致的高频字，剩余异常项单独确认。数据包与图形数据的许可证不同，应在后续资产接入时随相应来源保留；不能仅依据 cnchar 项目的 MIT 许可推断所有图形数据也使用 MIT。

## 可选方案与推荐顺序

| 方案 | 做法 | 收益与代价 |
| --- | --- | --- |
| 1. 按字逐笔兼容，优先推荐 | 保留标准码，在核验的左点位置允许 `n/p`；结合本次日志允许 `s`，为替代附加独立代价 | 与具体问题对应，污染范围较小；需要笔序变体对齐和排序验证 |
| 2. 构件模板生成标注 | 给宀／忄／心／冖等确认左点，利用构件分解及逐笔映射扩展到其他字，再由字形核验 | 减少逐字维护；需要处理嵌套构件、笔顺不同和分解缺漏。只查部首字段会漏掉非主部首中的构件 |
| 3. 有界的通用撇／点兜底 | 没有标注的字允许少量高代价替代，受替代次数、候选数量约束 | 可以补漏；最容易扩大错误候选，适合作为后备通道 |
| 4. 用户确认后的习惯适配 | 明确选中目标字后，累计其已确认左点位置的写法，适度调整兼容代价，并用语境重排 | 有望降低重复纠错；要防止错误选字被反向学习，不应凭一次提交生成永久规则 |

推荐先实施1，用2维护数据；3保持保守，4待有独立测试后加入。初期用宀、忄、心、冖等已复核位置；火部方向例外和“膝”等笔顺冲突单独处理。

例如“宝”的标准码 `nnzhhshn`，只在第二笔解释为 `{n,p,s}`，可兼容 `npzhhshn`／`nszhhshn`。第一笔和最后一笔仍按普通点匹配。“快”标准变体 `nnszhpn` 则只在第一笔兼容，其他已收录的忄笔顺变体必须各自确认左点索引。

左点兼容是已知写法变体，建议使用独立的小代价，不与轨迹不确定性的“最多一处补救”共用预算。允许一个字的多个已核验左点，同时保留通用识别补救的限制。手动指定类别和严格模式继续遵守明确输入规则。

实现时有三个必须处理的现有入口：

1. 左点位于首笔时，输入 `p/s` 也必须检索原始首码为 `n` 的相关字，否则后续匹配规则没有机会生效。
2. 当前模糊候选把只含单一类别解释的证据走严格查询快路径。要区分自动识别与手动锁定，不能因为自动识别“十分像撇”就跳过字形兼容。
3. 当前前缀匹配缓存仅按标准前缀保存结果。加入按字标注后，同样前缀的两个字可能兼容位置不同；缓存必须包含对应标注／变体，否则会复用错误匹配结果。

排序需要同时看完整笔序、兼容代价、字频和语境。现有“完整且无需替代优先”可能继续让较短的竞争字压住刚补回的目标字，应在对照测试中检查，而不是只验证目标字存在于候选集合。前缀查询应持续保留兼容字，不能仅等完整字写完才补救。
