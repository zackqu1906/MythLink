## 目标与语义

将忄、方、万、刀、力、乃、匕、及、火、母、辶、廴、匚、囗全部纳入组件编码范围。
用户仍然逐笔输入；解码器可以把若干笔解释为一个组件 token，并与其余笔画、组件组成候选字。
已登记的组件写法是编码路径，不消耗纠错预算，也不生成换序纠错提示。
真正的笔形替换、漏笔、多笔仍由既有识别与整字纠错处理。

组件 token 与书写顺序分离：同一组件可有多个实现路径；不同组件也可能具有相同五类笔画串。
组件不是“相邻笔画串的别名”，更不是把所有笔画任意重排后归并。

## 当前代码及约束

1. `stroke_dictionary_orders.py` 保留已有词库中笔画类别计数相同的变体，另有经位置核验的艹例外。
   这只是在过滤已有整字编码，既不定位一般组件，也不自动产生其在其他字中的写法。
   `Counter` 相同无法证明变化发生在同一个组件里。
2. `StrokeDictionary.candidates()` 按五类笔画串前缀召回；`fuzzy_candidates()` 加入识别证据、
   折笔细分、完整匹配优先级、字频、上下文，并在若干路径提前返回。
3. `WholeCharacterCorrector` 的替换、缺失、多余、相邻换序属于整字编辑解释。
   不能用它来实现正常组件编码。
4. `stroke_folds.fold_adjustment()` 依赖共同参考前缀；`StrokeVectorModel.cost()` 要求候选编码
   与向量模板编码一致且等长。组件换序需要显式逐笔映射，否则这些证据不能正确复用。
5. 当前向量重排只移动完整精确候选在各自层级中的位置，无法使新召回的组件候选与其共同竞争。
6. `promote_completed_fuzzy()` 和 `merge_candidates()` 有保护首选／预留位置的策略。
   组件编码应在普通候选排序之前合并，不走整字纠错预留槽。
7. 本机没有可靠的跨笔绝对位置输入。现有笔画向量可提供方向、相对长短；
   左右／上下／包围关系首先来自字典分解树，不能当作已经测得的手写空间证据。

## 首批组件规则

以下是要支持的规则族，不代表每个变体已经完成逐字数据核验。
只对具有可信组件归属及笔画映射的实例启用；参考码以当前字形数据的实际序列为准。

| 组件 | 实现路径与约束 | 回归字例 |
| --- | --- | --- |
| 忄 | 两点后竖、点竖点、竖后两点；两点在细笔形层仍需区分 | 快、情、怕、慢、惯 |
| 方 | 末尾折钩与撇的两种次序 | 放、房、访、防、芳 |
| 万 | 横后折钩／撇的两种次序 | 万、迈、劢 |
| 刀 | 折钩／撇交换；保持刀自身身份 | 刀、切、招、初 |
| 力 | 折钩／撇交换；与刀同五类码时保留两个解释 | 力、加、功、动 |
| 乃 | 折钩／撇交换；不能因外形相近改认成及 | 乃、奶、仍、扔、秀 |
| 匕 | 撇／竖弯钩交换；限定真实匕组件，排除七等相似片段 | 匕、化、花、华 |
| 及 | 撇与折笔的次序变体，末捺保留；不自动删并笔画 | 及、级、极、吸 |
| 火 | 两侧短笔先写／中间长撇捺先写的已登记路径 | 火、伙、秋、炎 |
| 母 | 点横点与先横后两点等已登记路径；区分每中的变体及毋 | 母、姆、拇、每 |
| 辶 | 内部后写辶、先写辶后内部两种组件调度；维持各部笔画归属 | 过、近、这 |
| 廴 | 内部与廴的先后调度；保留自身折笔形态，不与辶合并 | 延、建、廷 |
| 匚 | 横→内部→竖折，以及先写框再内部；组件允许中途挂起 | 区、医、匹 |
| 囗 | 左竖与横折→内部→底横，以及先封框再内部；不将口等同囗 | 因、国、园、回 |

保留既有艹规则与已收录整字变体；迁移时单独标记为 legacy 路径。
未被新组件模型解释的旧编码继续可达，不能直接清理掉。
火／灬、刀／刂等变体不按字源自动互换；若后续支持，须单列形态与映射。

## 数据模型

建议新建 `stroke-components.json`，不改变现有 `stroke-order-components.json` 的 v1 契约。
数据分成两层：

- 规则层：稳定组件 ID、形态、笔画角色、允许的次序模板、允许的内部／外部调度、来源与核验状态。
- 实例层：字形参考编码、组件分解树、结构关系、每个组件在整字中的笔画索引、规则版本。

示意：

```json
{
  "character": "快",
  "referenceCode": "nnszhpn",
  "components": [
    {"id": "heart-left", "form": "忄", "strokeIndices": [0, 1, 2], "treePath": [0]}
  ]
}
```

对包围结构，`strokeIndices` 可以不连续；需额外记录内部子节点和关闭框架的动作。
不能用 `start + length` 代替一般组件映射。

构建器可以复用 `build_stroke_order_components.py`、`build_left_dot_annotations.py` 中的
IDS 分解及 Make Me a Hanzi `matches` 递归映射；用当前字形路径及参考编码逐一核验。
来源笔数、笔画归属、字形版本不一致时输出跳过原因，不能仅按笔数强行对齐。
顶层自身就是目标组件的字也应收录。

结构资料只证明组件归属，不证明某个变体在用户中常见。写法白名单与来源核验须另存。

## 解码：笔画与组件并行的有界图搜索

新增 `stroke_components.py`（规则／实例装载）和 `stroke_component_decoder.py`（匹配）。
普通笔画边与组件实现边共同构成编码图，搜索结果是多种解释路径。

例如：

```text
观察：n s n z h p n
解释一：逐笔 n / s / n / z / h / p / n
解释二：COMP(忄, 点竖点) / z / h / p / n
匹配：快 = COMP(忄) / 夬
映射：expected_to_observed = [0, 2, 1, 3, 4, 5, 6]
```

这里解释二没有修改用户的任何一笔；映射只用于读取参考字形的笔形、向量和展示状态。
同类笔画可能导致多个映射，必须保留有限个可行映射再结合细笔形／向量判别，不能随意选一个。

具体要求：

1. 在旧 `by_initial` 筛选之前建立组件入口索引，否则首笔改变（忄、乃等）的字根本无法召回。
2. 保留原始逐笔路径，不能看到 `nsn` 就把它全局替换成忄。
   只有候选分解树中有相应组件实例的路径才可匹配。
3. 中途输入也可匹配组件状态。只写了部分组件时保留多个解释，不能强制归约为完整 token。
4. 匚、囗通过 open→内部子树→close 的动作调度实现；先写框是另一条登记路径。
   组件可以作为语义整体，但输入事件不必连续。辶、廴则调度外部与内部子树的先后。
5. 不全量展开一个字所有组件的排列组合；以组件自动机共享规则，运行时有界搜索。
   搜索宽度／每组件映射数／候选池大小须通过延迟与召回评估确定，限制写入日志。
6. 相同字通过多个路径出现时采用最佳有效路径，保留来源列表便于解释；不因路径更多重复加分。
   后续如引入概率求和，需要先做路径去重及概率校准。

建议匹配结果字段：

```text
char, reference_code, observed_code
match_type = literal | component | fuzzy | whole_character
is_complete, encoding_valid, physical_compatible
component_path, order_variant, expected_to_observed
component_cost, recognition_cost, corrections
```

组件的有效写法用 `match_type=component, encoding_valid=True, corrections=[]`。
若同时有识别替代，另存该替代对应的观测笔索引；组件归约本身不进入 corrections。
`exact_match` 当前兼有多种用途，不能简单置 True 来绕过旧限制；调用方应逐步改读显式语义字段。

## 与排序的关系

先将逐笔与组件召回结果合并，再计算所有证据，最后按字去重、截断；不能先取旧 top-30 再加组件分。

建议完整有效编码候选共同竞争，组件路径可进入首选；前缀、识别替代、整字修复保留明确的匹配状态。
前缀仍应可见，但未完成组件不享受完整匹配奖励。
保留现有真实纠错的独立入口与预算，但去重时正常组件解释优先于“换序修复”解释。

对每条路径计算工程代价（越低越好）：

```text
S(path, char) = recognition_cost
             + component_variant_cost
             + fold_cost(mapped_evidence)
             + w_vector * vector_cost(mapped_evidence)
             + frequency_prior
             - w_context * language_bonus
             + completion_adjustment
S(char) = min S(path, char)
```

- 参考写法与常见组件写法可具有不同习惯先验；这是编码路径的先验，不是 edit penalty。
- 不能对“组件数量”统一加分，否则部件多的字会天然占优。
- 不能重复计入旧变体字频和新组件先验。字频／上下文只对同一路径中的字计一次。
- 复用现有字频和上下文特征，新增组件代价先保持保守，再通过回放调权。
  当前向量权重 1.75 是在旧候选范围上选出的，扩大竞争范围后需要重新验证。
- 对缺少模板／映射的候选采用明确的中性处理，不能把缺数据当作完美匹配，也不能直接剔除。

折笔与左点：将 observed evidence 按 `expected_to_observed` 投影到参考字形索引，
再计算折笔细分与位置特定左点证据。投影只产生候选局部视图，不改变原始 evidence。

向量：同样先映射，再逐笔比较方向与相对长短。包围结构只是事件顺序改变，不需要虚构空间位置。
手动输入无向量时照常由编码、字频与上下文排序。

迁移时把旧 `fuzzy_candidates()` 的提前返回收敛到同一普通候选出口，组件开关独立于模糊／纠错开关。
`promote_completed_fuzzy()` 只处理真正识别替代；`merge_candidates()` 继续服务整字修复。
组件候选不占修复预留槽，也不因这个位置保护策略被禁止进入首选。

## 展示与个性化

输入轨迹保持用户原有顺序。候选字形利用映射标记已写笔画，不能再用“前 N 笔”给包围结构着色。
组件写法不标红；必要时仅显示“组件匹配：忄”等说明。
真正的识别替代和增删笔仍按原有语义显示。

用户选择候选后，可记录组件 ID、写法 ID、上下文和选择结果，形成组件级书写习惯先验。
只更新已登记写法的偏好，不把一次选择自动变成任意新排列规则；手动改笔与普通选字分开记录。

## 接入顺序与验收

1. 数据：登记全部 14 类规则，生成已核验实例及覆盖／跳过报告；含既有艹兼容。
2. 解码：纯模块支持组件前缀、跨首笔召回、包围调度与逐笔映射，输出解释，不改 UI。
3. 排序：在完整测试程序接入统一普通候选池；折笔、左点、向量使用映射；保留关闭开关。
4. 展示：组件候选正常着色，真实纠错单独展示；记录分项排序及搜索截断。
5. 回放通过后再接主程序；两处入口共享同一解码与评分逻辑。

必要验证：

- 14 类逐一覆盖参考与登记变体；多个组件组合；中途输入／撤销／继续书写。
- 新写法自然推广到未手工枚举整字编码的字，而非仅让旧词库测试通过。
- 同码不同组件：刀／力、匚／相似连续片段；无真实组件归属不得触发。
- 同类笔画映射歧义、非连续囗索引、先封框后写内部、辶／廴先后调度。
- 组件路径零纠错预算／无红色提示；组件之外的增删替换仍进入真实纠错。
- 未完成时不误报整字完成；变体完整输入能参与普通候选首选竞争。
- 映射后的折笔、左点及向量与对应参考顺序输入具有一致的物理证据解释。
- 关闭识别模糊／整字纠错时，已登记组件写法依然可用。
- 数据缺失中性退化；旧字库所有字符与已有编码继续可达。

评估分开报告：组件目标召回率、top-1／top-5、参考写法退化、前缀误触发、平均／p95 延迟、
候选池截断率。合成换序验证规则与映射正确性；真实自由书写数据才能评估识别与排序收益。
无空间测量输入时不宣称已经识别组件的实际摆放位置。
