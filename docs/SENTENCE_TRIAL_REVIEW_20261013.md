## 关键问题及证据

### 1. “霓”被候选范围排除，第三句存在配置导致的阻塞

三轮 `common_only=true`。字库有“霓”，但3500常用字集合没有它，因此候选过滤会将它排除。第三轮第三字位置用了69次笔画识别，提交了“零、雾、雹、雾”四次，始终未得到“霓”。不能把这次失败都归因于笔画模型或用户不会写。

字库还接受多个“霓”的笔序，例如 `hnzsnhpnpshzhhpz` 与 `hszsnnnnpshzhhpz`。目前实验评分只取第一条为真值，用户采用其他已收录笔序时仍可能被计错。

### 2. 错误出字多数发生在点击提交链路

按原始日志中出字前0.5秒内最近的SDK点击或轨迹决策关联：36次提交紧跟SDK点击，14次方向选字，4次标点；16次错误提交中，14次紧跟SDK点击，2次方向选字。

- 第一句8.625秒：只有 `h` 就提交“一”，目标为“穿”。
- 第一句78.422秒：`psz` 就提交“亿”，目标为“向”；这三笔也是“向”的前缀。重写成 `pszszh` 后才得到“向”。
- 第一句50.187秒：无待确认笔画时SDK点击提交联想“推”，目标为“画”。
- 第二句79.906秒提交“停”后，80.094秒再次点击提交无笔序联想“止”，间隔约188ms。此时原文还在逗号位置，随后需要连续回退。
- 第一句96秒：方向手势在无笔序状态选到联想“到”，实际目标为句号。

这些记录确认了“过早提交、连续点击提交联想、错误方向选择”三种表现。日志没有用户意图标签，不能据此把全部14次点击相关错误都判定为SDK误触；还可能是主动确认了错误候选，或没注意当前候选／标点位置。需要对典型轨迹做人工复核。

### 3. 笔画与笔序不稳定，且候选排序会放大纠错成本

在线五类笔序符合率合并为200/283＝70.7%，另外7笔没有真值（第二句在逗号位置继续书写），3笔为已知字符的多余笔画。分类统计为：

| 类别 | 正确 / 样本 | 符合率 |
| --- | ---: | ---: |
| 横 | 47/70 | 67.1% |
| 竖 | 44/60 | 73.3% |
| 撇 | 32/46 | 69.6% |
| 点／捺 | 37/54 | 68.5% |
| 折 | 40/50 | 80.0% |

这些数值是“识别结果与当前目标字第一条字典笔序的符合率”，不是有人工逐笔真值的模型准确率。错误出字后目标位置会向后偏移、笔序变体会被计错，也会混入写错笔序／画法的情况，不能直接判定哪一类模型最差。

“回”是明确的候选竞争案例：其标准笔序 `szszhh`，但只写到 `szsz` 时，“出”与“回”均可匹配；无模糊、无语境的字典候选也将“出”排在“回”前。用户两次用 `szsz` 提交“出”，后来仍用 `szsz` 通过方向选字选到了“回”。这表明除了书写识别，还有首候选确认习惯和候选排序的问题。

### 4. 当前没有显示出连接或计算性能是主要瓶颈

三轮采样统计均预热200/200，缺包和重置计数均为0。平均笔画识别计算为34.5ms、33.0ms、33.3ms，约为33.6ms总体加权平均。已记录队列年龄为0，推理批次最高约16ms。日志支持“主要时间花在输入与纠错交互”，不足以证明整个系统没有延迟，也未测量完整落笔至最终出字延迟。

## 下一轮优先处理

1. 开始前检查原文是否在当前候选范围内；提示“霓”这类不可输入字符，并提供切换全字库或改原文的明确入口。
2. 为点击确认和联想确认分别记录触发来源；复核约188ms连续出字样本，评估重复点击抑制和联想确认保护。不要将保护策略过度扩大，正常联想已贡献10个正确字。
3. 增加“写到完整字仍未确认”的提示，尤其是“向”被前缀“亿”抢先提交、“回”与“出”竞争的情况。
4. 给不会写的字提供完整标准笔序和下一笔提示，并区分五类笔画与具体笔形。对现有字库变体采用兼容评分，避免把字库自己接受的写法计错。
5. 复测时把常用字顺畅句、容易混淆的字、低频字分开；增加“误触／选错／不会写”的人工标记，才能从同一批日志分离模型错误和交互错误。

当前结论：常用句子能够纠错完成，联想有效；熟练度、点击确认保护、候选竞争和输入范围检查仍明显影响可靠性。本次是单人三句话的探索性试用，不能据此外推所有用户或长期平均输入效率。
