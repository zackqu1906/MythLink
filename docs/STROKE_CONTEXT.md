# 万象上下文模型（2026-11-03）

## 为什么换

旧的上下文资源 `stroke-context.json.gz` 来自 Tatoeba 约 8.8 万句和 500 篇维基百科，共约 230 万字，而且每个上文只保留 8 个后继字。在 2026-10 的整句试写里，要写的字只有 18% 落在这 8 个里。其余情况下，合理和不合理的字拿到的上下文分数一样，所以前几笔常常排出明显不合理的高频字。

## 来源

数据来自 [rime-wanxiang-data](https://github.com/amzxyz/rime-wanxiang-data)，许可是 CC BY 4.0。下载后放在 `tmp/wanxiang/`，这个目录不进仓库。

- **语法模型** `wanxiang-lts-zh-hans.gram`（LTS 版本，418 MB）：用约 48 GB 语料训练的词级 n 元模型，语料包括问答、博文、公众号、评论、歌词、新闻、百科等。
  - 文件格式是 Rime::Grammar/1.0，内部是一棵 darts-clone 双数组字典树。
  - 每个键是“上文词 + 下一个词”拼起来的字串，值为 `int(log(score) × 10000)`。
  - 读取方式参照 librime-octagram（BSD-3），没有使用万象的任何代码。
- **词库** `dicts.zip`（dict-nightly 版本）：用了其中的 `jichu`（约 149 万个带权重的词）和 `zi`（单字频率）。

## 怎么构建

脚本是 [build_stroke_context_wanxiang.py](../tools/build_stroke_context_wanxiang.py)，约 2 分钟。

对已写文字的末尾 s（1–3 个字），下一个字 c 由两部分打分，各自在上下文内归一化后各占一半：

- **跨词**：语法模型里 s 后面接以 c 开头的词。
  - 如果有精确的键 s+c，得分取 exp(值)。
  - 如果只有更长的键以 s+c 开头（后面跟的是多字词），给该上文最低精确分的一半。
  - 不同长度的键不能直接比较分值，因为键越长值越大，比如“今天天气”18.4、“我们”11.5。下面两种做法都试过，回放结果都变差，所以没有采用：
    - 把保底分按“以 c 开头的词有多常用”放大或缩小；
    - 直接查“s + 常用词”的分值。
- **词内**：词库里所有在 s 后面接 c 的词，按词的权重累加。

**存储和裁剪**：
- 存成和旧资源相同的格式（`[总数, 后继字, 伪计数]`），排序代码不用改。
- 单字上文全部保留，每个最多 200 个后继字。
- 二字上文保留 2.5 万个，其中 2 万个是最常用的二字词；三字上文保留 1.2 万个。
- 单字频率缩放到旧资源的总量，所以 `stroke_bonuses` 的字频项仍在原来的尺度上。

结果：44,099 个上文、14,392 个字的频率，压缩后 4.9 MB，加载约 0.2 秒。体积是这个设置两倍的版本，回放结果几乎一样。

## 前几笔加大上下文权重

笔画少的时候墨迹信息少，所以前 3 笔（`EARLY_STROKES`）的语言加分乘以 1.5。这个系数只对万象模型生效，旧资源和测试里自己构造的模型都不加权。

选择依据（小版本模型）：
- 系数 1.5 在第 1–3 笔明显更好，第 4–5 笔略差，所以只用在前 3 笔；
- 系数 2.0 在各笔数上都不如 1.5。

## 回放结果

回放的是 136 次已完成试写里，每个已提交字的每个前缀（最多 8 笔），共 1,938 个状态。候选流程与完整测试程序一致：常用字表、模糊匹配、部件、前缀向量。表中数字依次是首选／前 6／MRR。

| 已写笔数 | 旧资源 | 万象（含前 3 笔加权） |
| --- | --- | --- |
| 1 | 7.3% / 20.6% / 0.125 | 10.5% / 27.1% / 0.173 |
| 2 | 11.6% / 33.0% / 0.205 | 15.2% / 45.2% / 0.261 |
| 3 | 16.7% / 54.9% / 0.328 | 23.0% / 59.3% / 0.375 |
| 4–5 | 32.9% / 64.7% / 0.467 | 38.9% / 65.8% / 0.502 |
| 6 以上 | 47.5% / 69.7% / 0.563 | 48.0% / 69.7% / 0.568 |
| 全部 | 24.9% / 50.6% / 0.356 | **28.8% / 54.9% / 0.393** |

- 上下文覆盖到目标字的比例从 18% 升到 59%。这是 147 组不重复的“上文 → 目标字”，取 2 字和 1 字上文。
- 单次查询耗时中位数约 41 ms，旧资源约 40 ms。

## 接入

- `StrokeContext(model='wanxiang')` 读新资源，默认的 `StrokeContext()` 仍读旧资源。所以**主程序暂时不受影响**。
- 完整测试程序默认用万象模型，`--context-model legacy` 可以切回旧资源对比。所用模型写入日志（`context_model_settings`）和实验报告（`context_model`）。
- 已有的界面测试是按旧资源写的，所以 `load_window` 固定用旧资源。
- 第三方声明见 `THIRD_PARTY_NOTICES.md` 的 “Wanxiang context data” 一节。

## 局限

- 只用了你一个人的试写回放，混合比例和加权系数也是在这些数据上选的，结果偏乐观。
- 语法模型的分值没有严格的概率含义；只作为多字词开头出现的后继字，给的是粗略的保底分。
- 没有做个人化。你的上屏记录可以作为下一步，在这份模型之上做个人加权。

## 复现

```powershell
.runtime/venv/Scripts/python.exe tools/build_stroke_context_wanxiang.py
```

需要先把 `wanxiang-lts-zh-hans.gram` 和解压后的 `dicts.zip` 放进 `tmp/wanxiang/`。两个文件的 SHA-256 写在资源的 `sources` 字段里。
