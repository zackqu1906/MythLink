# OCR / 图片 → DeepSeek context 实测（2026-11-09）

结论：现有火山 `deepseek-v4-1-flash-260910` 支持图片输入，已实际调用成功。OCR 文字也能经过同一个模型提炼软件类型、主题和对话上文；短输出明显降低等待，但当前质量和延迟都不足以承诺固定 SLA。

## 当前实现

- `screen_context.py:147` 调用 macOS Vision Accurate OCR，中英识别；每条结果包含 `text`、`confidence`、`box=[x,y,w,h]`。框坐标归一化至 0–1，转成左上角原点；文本块不一定等于完整消息。
- `screen_context.py:44` 的规则负责聊天区域、标题、时间、相邻行合并、气泡角色及 16 块/2400 字限制，图片识字本身由 Vision 完成。
- 当前源码整窗识字；自动模式再过滤。旧微信记录只保存了 14 条 OCR，因此本次 OCR 对照重新调用当前 `recognize_image`，得到微信 47 行、Codex 72 行，未用旧裁剪结果代替整窗 OCR。
- 生产 `llm.py:258` 的火山请求只构造 `input_text`，尚未接入图片/上下文提取实验。

## 实验条件

两张经用户明确授权的本地截图，均来自 2026-11-06：微信 17:50 的触摸板首包超时讨论（1760×1426）；Codex 15:29 的“更新主项目 SDK”讨论（2400×1241）。没有把这些历史画面当作当前桌面状态。

接口为 `https://ark.cn-beijing.volces.com/api/v3/responses`，模型为项目实际配置的 `deepseek-v4-1-flash-260910`；关闭 thinking，非流式，最大输出预算 3000。图片为 PNG Base64，`detail=original`。API Key 不写入报告。

详细图片实验只给图片，不给 OCR 或应用名称。后续短输出对照给两种输入相同的操作系统 application 标识，输出相同五字段 JSON；每张每种输入重复 3 次。两组提示词 v3/v4 的区别是 v4 解释分栏输入；图片短输出和整理后 OCR 都使用同一 v4 提示词。

整理后的 OCR：聊天应用复用现有 `filter_context` 的会话/发言人规则，输入区 OCR 独立提供；其他应用按文本框水平重叠和 0.015 间隙分栏，所有非纯符号栏仍供 LLM 判断。这只是实验性几何启发式，并非通用布局识别器。

## 速度

单位：秒。API 耗时从开始 HTTP 请求到完整响应；OCR＋API 不含截图、载图、JSON 编码、应用调度和后续语音处理。图片输入该列等于 API 耗时。每种短输出仅 6 次，不能估计可靠 P95 或服务 SLA；同图重复请求部分命中服务端缓存，调用按组顺序执行、未随机化，网络/负载可能影响对比。

|---|---:|---:|---:|---:|
| 图片详细输出 v1 | 2 | 6.04–8.59 | 7.32 | 7.32 |
| 图片详细输出 v2 | 2 | 7.60–10.27 | 8.94 | 8.94 |
| 逐行 OCR＋坐标，短输出 | 6 | 1.59–1.95 | 1.89 | 2.64 |

整理后 OCR 的 6 次总耗时为 2.30–2.76 秒，API 为 1.53–1.94 秒。本地 OCR 首次有启动开销，后续微信约 0.57–0.60 秒、Codex 0.81–0.86 秒。图片短输出存在 20.75 秒、21.16 秒的长尾，不能据此断言全部来自视觉编码。

整理后 OCR 的输入 token：微信 511，Codex 2215；输出 96–138。图片短输出的输入 token：微信 1329，Codex 1286；输出 105–131。因此文字输入不一定总比图像 token 少；布局、输出预算及服务负载都影响延迟。

## 质量核对

- 详细图片输出能提取六条微信消息、self/other、报错字段以及未发送草稿“未来语音输入法”；Codex 能提取中央讨论，较旧规则结果保留了更多主题信息。
- 图片 v1 把微信联系人侧栏放入 key_facts，并把“源码应用”误读为“溯源应用”；v2 修正了后者，但仍在 uncertainties 提到侧栏，且把一条 Codex 回复拆成多条消息。
- 裸 OCR＋逐行坐标：微信 3/3 含侧栏干扰，首次甚至误称“妈妈、哥确认触摸板手势”；说明仅附上坐标并不保证文本模型理解空间关系。
- 整理后 OCR：微信 3/3 不再混入联系人；但 1/3 把“可以做适配”改为“已做适配”，并有把原文“回复”改为“恢复”的语义推测。不能把流畅摘要当作逐字准确。
- 整理后 OCR 的 Codex 2/3 正确输出 ai_assistant，另一次为 other；另有一次仍引入右侧仓库变更统计。已知应用类型宜从本地应用标识映射。
- 微信草稿：整理后 OCR 输入明确含“未来语音输入法”，但 3/3 返回 draft=null；图片短输出也只有 2/3 正确返回草稿。因此草稿/可编辑原文不能依赖摘要模型提取，继续使用输入法/AX 等已有可信源并保持只读 OCR 边界。
- 短输出的 uncertain 全部返回 false，不能把这个自报字段当作经过校准的置信度。

## 接入判断

推荐下一步采用“本地 OCR → 轻量区域/发言人整理 → 短 context 摘要”，并保留原始文字证据。软件名称/已知类型由本地应用信息确定；LLM 只提取主题和短摘要，不负责确定可编辑范围或代替真实原文。

低等待时间应由调度保证：录音开始时预取；应用/窗口/画面未变化时才复用缓存；录音结束只消费已就绪结果，超时则沿用已有规则 OCR context。现有 `resolve_context` 有 4 秒等待上限，正式接入时应显式处理跨窗口过期结果、预算和回退，不能仅增加一个同步 LLM 请求。

本轮只新增实验工具和结果文件，未修改生产 OCR、LLM 或语音链路。2 张截图的探索性结果不等于跨应用准确率验收。
